# 2026-07-07

## Notes

### Backlog: Record sharing architecture — ExportScreen is unreachable

Discovered as an unrelated architectural observation while auditing the new
Weight-record `sets` field for side effects (Health Sync + Export/Import/Share
paths). Not part of the Sets feature itself — no production code was changed
for this item.

**Repository Verified findings**

- `lib/features/export/export_screen.dart` defines `ExportScreen`, a share-card
  screen that renders a record's primary value (weight, distance, or duration)
  onto an image and shares it via `share_plus`. A repo-wide search for
  `ExportScreen(` finds **zero constructor call-sites** anywhere in `lib/`
  outside its own file — it is not navigated to from any route or widget.
- `record_detail_screen.dart:203` and `exercise_detail_screen.dart:310` both
  call `context.push('/share/${record.id}')`.
- The route `/share/:recordId` is registered in `lib/app.dart:107-110` as
  `builder: (context, state) => const ShareScreen()` — it does not read
  `state.pathParameters['recordId']` at all.
- `lib/features/share/share_screen.dart` (`ShareScreen`) is a static
  placeholder: it renders a share icon, a tagline, and a "beta" label
  (`_PlaceholderContent`, lines 28-66). It takes no record data and displays
  nothing derived from the tapped record.

**Why this is not being addressed in the current PR**

- It is unrelated to the Sets feature's scope (adding an optional `sets`
  field to Weight records) and was only surfaced as a side effect of auditing
  export/share paths for that feature.
- `ExportScreen`'s existing formatting logic (`_formatValue`,
  `_calcDaysSince`) was already checked as part of that audit and found to
  correctly exclude both `reps` and `sets` — so nothing there is broken by
  the new field. The dead/placeholder state of the sharing flow is a
  pre-existing condition, not a regression introduced by this work.
- Fixing or redesigning this would touch navigation and a user-facing feature
  (record sharing) well beyond a "smallest possible change" bugfix, and
  deserves its own scoped task rather than a drive-by fix bundled into an
  unrelated PR.

**Recommended future investigation**

- Decide the intended fate of `ExportScreen`:
  - Wire `/share/:recordId` to `ExportScreen`, passing the resolved
    `Exercise`/`Record` (or the relevant primary value + date) instead of
    `ShareScreen`, if the share-card feature is still wanted.
  - Or remove `ExportScreen` (and its supporting files: `export_models.dart`,
    `clean_frame.dart`, `rough_frame.dart`, `frame_painter.dart`) if the
    share-card design was superseded and is now dead code.
  - Or treat `ShareScreen`'s "beta" placeholder as the intended near-term
    state and track the real share-card redesign as a separate, larger
    feature.
- Any future redesign of the sharing architecture should include a focused
  review of the affected Share/Export paths to ensure they remain consistent
  with the Record model (including the optional `sets` field, if still
  applicable).
